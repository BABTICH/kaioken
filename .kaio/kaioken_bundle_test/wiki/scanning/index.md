# Scanning the Repository

The `packages/scan/src/scan.ts` module orchestrates the initial traversal of the repository and assigns preliminary risk flags to files. This is the first step in the analysis pipeline. The `scan` function is the entry point, responsible for recursively walking the directory tree and identifying potential sensitive files.

The `walk` function is recursive and handles the directory traversal. It takes an absolute directory path `absDir` and a relative path `relDir` (relative to the root of the repository) as input.  It also uses an `IgnoreStack` (defined elsewhere, not shown here) to manage files and directories that have been explicitly excluded via `.gitignore` or similar mechanisms. Each invocation of `walk` calls `readFile` to process each file it encounters.

The `readFile` function reads the contents of a single file.  It first reads a "head" – a short prefix of the file.  This "head" is used for language detection, binary detection, and initial risk assessment. The size of the head is limited by `DETECTION_WINDOW` (64KB) to improve performance, and the entire file is read only if it’s smaller than `DEFAULT_MAX_READ_BYTES` (4MB).  Large files (larger than `DEFAULT_LARGE_BINARY_BYTES`, 1MB) are treated as binary for the purpose of file type detection to avoid overwhelming the system. After reading the head, it computes a hash of the entire file using `hashStream`. The function returns a `FileRecord` (defined elsewhere) containing the file's absolute path, relative path, file size, hash, head, and a boolean indicating whether it's a binary.  If the file cannot be read, it returns `null`.

The code utilizes helper functions like `toPosix` to normalize file paths to a POSIX-compliant representation, ensuring consistency across different operating systems in the generated artifacts.

Once `readFile` returns a `FileRecord`, `packages/scan/src/risk.ts`'s `classifyRisk` function is called to assess the risk level. This is where more detailed inspection happens.

The `classifyRisk` function receives a `RiskInput` – containing the file's path, size, hash, head, and whether it's binary – and returns an array of `Risk[]` (also defined elsewhere) representing the identified risks.  It employs a series of checks:

*   **Credential Filenames & Content:** It uses `isCredentialFilename` to determine if the filename is suggestive of credentials (e.g., "credentials.json").  If so, it proceeds to use `hasCredentialContent` which looks for patterns indicative of sensitive data, like AWS access keys (`AKIA...`), GitHub tokens (`gh...`), Stripe secrets (`sk_live...`), and generic secrets matching the `GENERIC_SECRET` regex.  `CREDENTIAL_CONTENT` is an array of regular expressions used for this purpose.
*   **Generated Code:** The code checks for common generated code patterns using `isGeneratedPath`, `hasGeneratedBanner`. The lists `GENERATED_PATH_SEGMENTS` and `GENERATED_FILENAME` help identify automatically generated files. `GENERATED_CONTENT` contains regexes like `"Code generated by"` and `@generated`.
*   **Lockfiles:** The presence of `LOCKFILES` such as `package-lock.json` or `yarn.lock` is detected. These are not flagged as risks but are important metadata.
*   **Binary Files:** `isBinary` classifies files based on their head.
*   **Environment Template Files:** Files ending in suffixes in `ENV_TEMPLATE_SUFFIXES` are considered templates and not real secrets, even if they contain credential-like content.
*   **Placeholder words:** Files containing words in `PLACEHOLDER_WORDS` are considered documentation.

The `looksLikeLiveSecret` function is crucial for preventing false positives. It applies an entropy floor to ensure that the detected string has sufficient complexity to plausibly be a live secret.  `isCertificateOnly` distinguishes between certificate-only PEM files and those containing secrets.  The `firstLines` function provides a way to look at a small number of lines from a file. The `basename` and `extname` functions provide the filename and extension from a path respectively.
