# The Symbol Index

This chapter describes the core data structures and processes involved in building the symbol index – a critical component of the repository analysis system.  The symbol index is a mapping from symbol names to their declarations within the codebase, enriched with location and metadata. It underpins the ability to answer questions like "where is `foo` defined?" and "what are all the uses of `bar`?". The process begins with parsing source files using Tree-sitter, continues with extracting relevant declarations, and culminates in the creation of an oracle for efficient symbol lookup.

The process hinges on a combination of Tree-sitter grammars and custom extraction logic.  First, the code is parsed with a Tree-sitter grammar (`packages/index/src/grammars.ts`).  `GRAMMARS` defines the supported languages and their associated wasm files and query files. Each language listed in `GRAMMARS` requires a corresponding `.scm` query file that directs Tree-sitter to identify relevant syntax elements.  These grammars are lazy-loaded by `loadGrammar`, which only initializes the `Parser` (`packages/index/src/grammars.ts`) once per process by using the `initParser` function.  The initialisation (`initialised`) prevents a costly call to `Parser.init()` from being re-executed.

Once the file is parsed, `extractFile` (`packages/index/src/extract.ts`) takes over. It leverages the grammar to find nodes representing declarations and processes them to extract information.  The `collect` function recursively traverses the parsed tree, guided by the provided query, to identify potential symbols.  `KINDS` lists the types of symbols we're interested in extracting, while `TYPE_LIKE` identifies nodes that often contain method definitions.

Several utility functions operate on parsed nodes to extract meaningful information. `signatureOf` (`packages/index/src/extract.ts`) extracts the declaration head (e.g., "function foo" or "class Bar"), stripping away the body.  `docOf` extracts the JSDoc/docstring above a declaration, and `pythonDocstring` specifically handles Python docstrings.  Identifying exported declarations is language-specific (`isExported`), distinguishing rules like TypeScript’s `export` keyword from Python’s module-level assignments. Similarly, `isRestrictedMember` detects class members that are intentionally hidden, like `private` or `protected` fields.  `hasExportAncestor` verifies if a declaration is exported via an ancestor declaration (e.g., a module export). `enclosingDeclarationName` finds the name of an enclosing declaration, useful for resolving ambiguous names.  The logic surrounding comments is handled by functions such as `outermostWrapper`, `widenLoneSpec`, `stripCommentMarkers`, and `stripPythonString`, which are used to correctly extract and clean documentation comments.

The extracted symbol data is structured as `SymbolRecord` objects. These records are then used to populate the `SymbolOracle` (`packages/index/src/oracle.ts`), which provides a lookup mechanism for symbols. The `SymbolOracle` maintains two primary data structures: `byName`, a map from symbol name to a list of locations, and `byPath`, a map from file path to `FileMap` containing all symbols within that file. The `unknownNames` function identifies symbols claimed by a document but not present in the repository.  `exported` retrieves all exported symbols. The `symbolCount` property provides a quick overview of the total number of symbols indexed. This oracle provides a centralized and efficient way to query for symbol information, critical for the repository analysis system.
