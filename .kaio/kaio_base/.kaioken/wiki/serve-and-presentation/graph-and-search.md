# Graph and Search

This chapter covers two user-facing views in the `kaioken/serve` module: the interactive knowledge graph and the search results page. Both are server-rendered HTML generated by functions in `kaioken/serve/src/pages/`, and both consume data structures defined in `kaioken/serve/src/graph.ts`.

## Graph data model

The wire format for the graph view is defined entirely in `kaioken/serve/src/graph.ts`. It mirrors the graph structure the original graph engine emitted, but is rebuilt client-side from the already-parsed `Library`. The three node kinds are captured in `GraphNodeKind` (`"doc" | "file" | "section"`), and the three edge kinds in `GraphEdgeKind` (`"contains" | "links" | "source"`). These are the only edge relationships the UI understands.

`GraphNode` and `GraphEdge` are the basic shapes. `GraphStats` holds counts (node totals, edge totals, component counts), and `Graph` bundles nodes, edges, and stats together for serialization to the page.

The ID helpers are simple but load-bearing:

```ts
// kaioken/serve/src/graph.ts:51-53
const docId = (path: string): string => `doc:${path}`;
const fileId = (path: string): string => `file:${path}`;
const sectionId = (id: string): string => `section:${id}`;
```

Every node ID is prefixed with its kind, so the UI can route clicks without extra lookup. The prefixes also make collisions impossible — a file path and a document path are never the same string.

## Graph construction

`buildGraph(root: string, library: Library): Graph` is the sole entry point. It walks the `library` and emits nodes and edges with the same semantics the previous Python-rendered v1 graph had. The key decisions:

- **Sections are nodes with incoming `contains` edges** from their parent document. This lets the UI expand a document node to show its internal structure.
- **`links` edges** are emitted between documents that reference each other, derived from the wiki links already parsed by `readLibrary` — no new parsing happens here.
- **`source` edges** connect a document to the files it draws content from. This is how the UI can show provenance visually.

The `leadDoc(chapter: WikiChapter): WikiDoc | undefined` helper determines which document opens a chapter — the same rule the wiki navigation uses — and is used to give those lead documents a distinct visual treatment in the graph.

The `basename(path: string)` helper at the bottom is used for node labels so the UI shows `chapter.md` rather than a long path.

The function is a pure derivation: same `Library`, same `Graph`, always. It performs no I/O and no mutation, so it is safe to call per-request.

## Graph page

`graphPage(): string` in `kaioken/serve/src/pages/graphView.ts` renders the full HTML page for the graph view. It outputs a container div plus the serialized `Graph` as an embedded JSON blob, plus a script tag that imports the client-side renderer. The page itself is a shell; all interactivity (pan, zoom, filter, click-to-navigate) lives in the frontend graph engine, which is a ported asset (`graphEngineAsset.ts`) referenced by the page.

The page deliberately does no filtering server-side. The full graph is shipped, and the client filters by node kind, searches node labels, and collapses/expands `contains` subtrees. This keeps `buildGraph` cheap and keeps the UI snappy even for large libraries.

## Search page

`searchPage(...)` in `kaioken/serve/src/pages/searchView.ts:15-142` is the server-rendered search results view. Its signature is explicit about what the search backend has already computed:

```ts
function searchPage(
  site: Site,
  query: string,
  hits: readonly SearchHit[],
  semantic: boolean,
  kind: string,
  available: Record<string, number>,
  limit: number,
): string
```

The `hits` array is the ordered result list from the search engine; this page only formats it. The `semantic` flag switches the UI between "semantic" and "keyword" result rendering — notably, when semantic search is active, each hit shows a snippet from the matched section rather than the document title alone. The `kind` filter (doc, file, section) is passed through to gate which hit types are displayed, and `available` gives per-kind hit counts so the UI can show facet labels ("12 documents, 3 files"). `limit` controls how many hits the page displays; the caller truncates the array before calling.

`hitHref(hit: SearchHit): string` at the bottom of the file computes the navigation target for a given hit. It maps a `SearchHit` to a URL the serving layer understands — document hits link to the doc page, file hits link to the raw file viewer, and section hits link to the section anchor within the document. This is the only place in the search page that knows about URL shapes; the rest of the template stays agnostic.

The page renders a search form at the top (pre-filled with the current `query`), the facet counts from `available`, then the hit list. Each hit is rendered as a card with title, kind badge, and snippet, wrapped in an `<a>` from `hitHref`. The whole function returns a complete HTML string; there is no progressive enhancement — navigation happens via normal page loads, with the query parameter round-tripping through the server.
