# Kaioken Core Concepts: Action and Delivery Modules

This chapter covers the four executable modules that transform a verified knowledge graph into actionable output: `plan`, `verify`, `serve`, and `skillgen`, plus the `verifycore` variant that `verify` builds upon. These modules sit on top of the graph, impact, and provenance layers described elsewhere in this wiki.

## Module Architecture

All four modules follow the same structural pattern, enforced by the Kaioken monorepo conventions:

- Each lives in its own directory under `kaioken/`
- Each has a `package.json` with a `name` scoped to `@kaioken/{module}`
- Each exports a CLI entry point (`bin`) and a programmatic API (`main` and `types`)
- None of them import from each other directly; they communicate via the shared graph and impact modules

The reason for this strict separation is operational: `verify` and `skillgen` can run in CI without pulling in the HTTP server dependencies of `serve`, and `plan` can run headlessly. This keeps the dependency graph of each deployment target minimal.

## `kaioken/plan` — Workload Planning

The plan module is the entry point for deciding *what* the Kaioken system will work on. It has no runtime declarations of its own — it is a thin orchestrator that imports planning logic from the graph module (covered in the Planning Module chapter) and exposes it as a CLI.

Its responsibilities:

- Read the current graph state from the workspace's indexed artifacts
- Determine which artifacts are stale or missing (using provenance data from the provenance layer)
- Produce a structured plan of cards — discrete work items — that the user can review before any mutation happens
- Validate the plan against the schema before it is handed to downstream workers

The plan module intentionally has no write access to the graph. This is a design decision: planning must be a pure function of the current state and the user's intent, so that a bad plan can be rejected without side effects. If the plan is accepted, the actual graph mutations happen in the graph module's own execution layer.

## `kaioken/verify` — Pre-Deployment Verification

The verify module validates that the knowledge graph and its derived artifacts are consistent before they are served or published. Like plan, it has no exported declarations of its own; it is a CLI wrapper around the `verifycore` package.

The verification pipeline checks, in order:

1. **Graph integrity** — every artifact referenced in the graph resolves to a real file, and every document indexed in the graph still exists on disk
2. **Provenance soundness** — every artifact's provenance shows how it was created or fetched, and no artifact claims provenance it cannot substantiate
3. **Card validity** — every card generated by planning matches the card schema and contains no dangling references to graph nodes

The verification results are emitted as a machine-readable report. The exit code is non-zero if any check fails, which makes the module suitable for use as a pre-merge gate in CI.

The absence of a programmatic API in `verify` is deliberate — verification is a one-shot operation, and forcing callers through the CLI ensures they see the full report rather than silently catching an intermediate failure.

## `kaioken/verifycore` — The Verification Engine

`verifycore` is where the actual verification logic lives. It is the only module in this chapter with a real exported API surface. While no declarations are indexed here, the module's purpose is to provide verification logic for graph integrity, provenance soundness, and artifact validity checks. It supports compositional verification: the top-level graph verifier is a loop over artifact verifiers, and each artifact verifier is itself composed of smaller checkers (provenance, index entry, content hash). This means adding a new artifact type to the system only requires adding one more checker, not rewriting the verification orchestration.

`verify` delegates to `verifycore` through a subprocess boundary so that the CLI can capture the full report even if the verification process runs out of memory or crashes partway through.

## `kaioken/serve` — Presentation and Delivery

The serve module is the HTTP presentation layer (detailed fully in the Serve and Presentation chapter). It has no runtime declarations indexed here because all of its logic lives in the shared graph module's UI components; the serve module itself is a thin HTTP server that:

- Boots an Express-like application
- Mounts routes for `/docs`, `/cards`, `/files`, and `/graph` endpoints
- Resolves those routes against the graph module's rendering functions
- Applies the workspace theme (from the `_pi` infrastructure) to all HTML output
- Streams graph change events to connected clients via SSE for live updates

The module's singular responsibility is to map HTTP requests to graph reads. It has no write paths by design — all mutations go through the plan/verify pipeline, so the server can run with read-only filesystem access. This makes it safe to deploy in a container with a read-only root.

## `kaioken/skillgen` — Skill Template Generation

The skillgen module produces new skills (prompt-tuned workflows) for the Kaioken system. It is the generative counterpart to the curated skills that ship in `_pi/skills`. Its pipeline (covered in depth in the Skill Generation chapter):

1. Accept a proposal — a structured description of the new skill's trigger, inputs, and expected outputs
2. Select a skill template from the built-in template set (each template has a fixed scaffold: a `SKILL.md` manifest and schema files)
3. Instantiate the template with the proposal's parameters
4. Write the resulting skill files into the workspace skills directory
5. Run a light self-check (reusing `verifycore`'s single-artifact verifier) to confirm the generated files are well-formed

The reason skillgen lives as a separate module rather than inside the graph module is that skill generation is a *write* operation that requires template resolution, whereas the graph module is read-centric. Splitting it out keeps the graph module's write surface limited to artifact indexing.

All four modules share one invariant: they are stateless between invocations. Any state they need (graph index, provenance database) lives in the workspace, not in the module processes. This is what makes the whole system restartable and auditable — killing a `serve` process and restarting it yields identical output because the server never holds authoritative state.

The coupling between the modules is entirely through the graph: `plan` reads it, `verify` validates it, `serve` presents it, and `skillgen` extends the tooling that operates on it. No module ever reaches into another module's private state, which is why the dependency graph mirrors the conceptual flow: verification is the only module that depends on a shared engine (`verifycore`), and that engine is kept deliberately small so it can be embedded in CI without pulling in everything else.
