# Scan and Search Integration

## Pipeline Overview

The scan and search modules form the discovery-and-retrieval half of the kaioken workspace pipeline. Scanning traverses the repository to enumerate files, while search indexes and queries their textual content. Together, they let a caller move from "what files exist?" to "what do these files say about topic X?" without coupling to any specific storage backend.

## The Scan Module

`kaioken/scan/src/index.ts` is deliberately minimal. It exports no declarations of its own — it is a side-effect entry point that wires up the scanning machinery. The module exists to be imported for its initialization behavior, not to expose an API surface. This keeps the scanning logic modular: the actual traversal implementations live in the workspace infrastructure, and this file simply ensures the scanner is registered and available when the search module runs.

## The Search Module

The search surface is a single function in `kaioken/search/src/search.ts`:

```ts
kaioken/search/src/search.ts:3-22
export async function bm25Search(root: string, query: string, limit = 8): Promise<string>
```

`bm25Search` implements BM25 (Best Matching 25) ranked retrieval over the workspace rooted at `root`. BM25 is the standard probabilistic ranking function for keyword search — it scores documents by term frequency with length normalization and saturating term-frequency weighting, then penalizes terms that appear in many documents. Choosing BM25 here is a pragmatic call: it requires no training, works well on short queries, and is deterministic across runs, which matters for reproducibility in downstream modules that consume search results.

The function returns a `Promise<string>` rather than a structured list. The string is intended to be a formatted, human-readable digest of the top matches (paths plus snippets), which can be slotted directly into prompts or UI text generated by the serving layer. The `limit` parameter (defaulting to 8) caps the number of results to keep responses small and predictable.

## How They Fit Together

The integration pattern is: scan first, then search. The scan module primes the workspace state (ensuring the file index is populated), and `bm25Search` then queries against that primed state. Because `bm25Search` takes only a root path, a query, and an optional limit, it works as long as the scan has run — the search function does not perform its own traversal.

Typical usage in a downstream module (e.g., the graph or serve layer) looks like:

1. Import `kaioken/scan/src/index.ts` for its side effects to ensure the scan is active.
2. Call `bm25Search(root, query, limit)` with the workspace root and the user's natural-language or keyword query.
3. Feed the returned string into the calling module's output — whether that is a graph node, a card, or a UI response.

This separation keeps concerns clean: scanning owns file discovery and indexing state; searching owns ranking and retrieval. Neither needs to know about the other's internals, and both are replaceable as long as the side-effect contract (scan runs first) holds.
